# فينشي + ChatbotX — دليل التنفيذ والتشغيل

تاريخ المراجعة: 27 سبتمبر 2026. هذه حزمة تجهيز واختبار أولي، وليست شهادة جاهزية للإنتاج. لم تُشغّل حاويات ChatbotX أو تُربط حسابات العملاء في هذه البيئة. إصدار التشغيل المرشح `1.10.0`؛ مراجعة المصدر شملت أيضًا `main` الأحدث منه. تفاصيل الإصدارات في `sources.lock.json`.

## 1. القرار وما الذي سنستخدمه

نعتمد **ChatbotX Community منصة التشغيل الأساسية للرسائل وخدمة العملاء**. نستخدم لوحة VINCHI الحالية كإضافة للتجارة والمتاجر والطلبات. لن نبني صندوق رسائل أو تطبيق موظفين جديدًا من الصفر. الربط بين الجزأين يكون عبر API موثق، وليس بتعديل جداول ChatbotX مباشرة.

| المشروع الأصلي | الاستفادة في فينشي | قرار التنفيذ |
|---|---|---|
| ChatbotX | صندوق الرسائل، جهات الاتصال، المحادثات، التدفقات، الحملات، صلاحيات الأعضاء | الأساس الذي نطوره ونختبره |
| chatbotx-docker-compose | تشغيل الويب والعمال وقواعد البيانات والتخزين وRealtime | أخذنا إعداداته وعدّلنا نسخة مستقلة في هذا المجلد |
| chatbotx-mobile-app | تطبيق موظفين iOS وAndroid؛ توجد ملفات عربية ودعم RTL | نعيد استخدامه بعد نجاح الويب؛ أُعدّ قالب العلامة التجارية فقط |
| chatbotx-n8n | إجراءات جهات الاتصال والتدفقات والرسائل وwebhooks | اختياري لاحقًا؛ ليس شرطًا لتشغيل المرحلة الأولى |
| chatbotx-agent | أدوات CLI/MCP وتعليمات لمساعدة المطورين على استخدام API | اختياري للتطوير؛ ليس خادم الرسائل ولا خدمة العملاء |

وجود قناة داخل الكود لا يعني أن حساب فينشي حصل على صلاحيات مزودها، أو أن كل وظائف المزود متاحة. لا نعِد بحد عملي غير محدود للموظفين: سعة السيرفر والتحميل الحقيقي تحددان ذلك. لا نضيف HubSpot الآن لأننا سنكرر جهات الاتصال والمزامنة دون ضرورة مثبتة.

## 2. ما تم تنفيذه فعليًا

1. إعداد Docker Compose مشتق من المشروع الأصلي مع تثبيت إصدار مرشح، وإزالة Adminer وMailhog ومنافذ قواعد البيانات والتخزين المكشوفة.
2. تعطيل `RUN_DB_SEED`: ملف seed الأصلي ينشئ حساب تجربة معروفًا، فلا نستخدمه على سيرفر العملاء.
3. تعطيل migrations التلقائية وإضافة خدمة منفصلة لتشغيلها عمدًا، مرة واحدة، بعد النسخ الاحتياطي.
4. مولّد مفاتيح محلي ينشئ `.env` بصلاحيات `0600` ويرفض استبداله حتى لا نفقد مفتاح تشفير القنوات.
5. إعداد HTTPS وRealtime والتخزين عبر Caddy؛ تمرير روابط S3 الموقعة دون تغيير المسار أو Host. التخزين العام مقتصر على قراءة `public/`؛ الملفات الأخرى تتطلب توقيعًا وصلاحيات.
6. حماية تيليجرام على مستوى reverse proxy: مطابقة سر webhook ومعرّف بوت واحد. الأداة المرفقة تسجّل السر لدى Telegram بعد ربط البوت داخل ChatbotX.
7. إضافة فحص اتصال للقراءة فقط داخل لوحة فينشي. يفحص API العملاء ومساحة العمل من الخادم، ولا يستورد العملاء ولا يرسل رسائل.
8. قالب إعداد VINCHI للموبايل وملاحظات النشر، واختبارات محلية، وتوثيق النواقص وخطة الانتقال.

**غير منفّذ بعد:** تثبيت السيرفر، تشغيل ChatbotX فعليًا، تكامل Shopify، استقبال الرسائل الحقيقية، تفعيل الموظفين في منصة التشغيل الجديدة، نقل سجل Zoko/respond.io، بناء أو نشر تطبيق الموبايل. لوحة VINCHI المنشورة ما زالت تجربة خاصة لصاحب الحساب.

## 3. الترخيص وحدود النسخة المجانية

جذر ChatbotX مرخّص MIT مع استثناء `apps/builder/src/enterprise` بترخيص تجاري. وظائف مثل مجموعات فرق الصندوق، بعض سجلات التدقيق، وإعدادات العلامة التجارية على مستوى المنصة تقع في الجزء التجاري. لا نحذف فحوص الترخيص ولا نغير `NEXT_PUBLIC_EDITION=community` لتجاوزها.

مستودعا Docker Compose والموبايل مرخصان MIT؛ أُرفقت إشعاراتهما. ترخيص إضافة ChatbotX لـ n8n لا يحدد ترخيص n8n نفسه. يجب مراجعة شروط المكونات الخارجية قبل إعادة بيع الخدمة. هذه ملاحظة عن ملفات المشروع التي قرأتها، وليست مراجعة قانونية كاملة.

تم إنشاء النسخ في حساب `dalsolnet`، والتحقق من إتاحة القراءة والكتابة بتاريخ 28 سبتمبر 2026. لا تحتاج إلى Fork جديد.

- النظام الأساسي: https://github.com/dalsolnet/ChatbotX
- التشغيل (هذا المستودع): https://github.com/dalsolnet/chatbotx-docker-compose
- الموبايل: https://github.com/dalsolnet/chatbotx-mobile-app
- n8n: https://github.com/dalsolnet/chatbotx-n8n
- أدوات التطوير: https://github.com/dalsolnet/chatbotx-agent

توجد إعدادات فينشي في مجلد `vinchi/` بفرع `vinchi/staging-foundation`. اقرأ طلب المراجعة قبل دمجه في main. للتجربة من هذا الفرع:

```bash
git clone --branch vinchi/staging-foundation https://github.com/dalsolnet/chatbotx-docker-compose.git
cd chatbotx-docker-compose/vinchi
```

نفّذ أوامر الأقسام التالية وأنت داخل `vinchi/`. الملف المستخدم هو `vinchi/compose.yaml`؛ ملف `docker-compose.yml` في الجذر هو إعداد المشروع الأصلي وليس إعداد فينشي. الصور الرسمية تشغّل إصدار ChatbotX الرسمي؛ تغييرات كود Fork الأساسي تحتاج بناء صور خاصة وتحديث مراجع الصور.

هذه مستودعات عامة؛ لا تضع فيها بيانات عملاء أو مفاتيح أو ملفات `.env` أو نسخ قواعد البيانات. كود لوحة VINCHI التجارية الخاصة مستقل عن هذه الحزمة ولا يُرفع معها. احتفظ بأسماء التراخيص وإشعارات المؤلفين. راجع تحديثات upstream على فرع وتجربة staging، ولا تجعل الإنتاج يتبع main أو latest تلقائيًا.

## 5. السيرفر والدومين

نحتاج سيرفر Linux بمعمارية x86_64 لأن الصور المحددة تستخدم `linux/amd64`، مع Docker Engine وCompose v2. كنقطة بداية تقديرية للتجربة: 4 vCPU و8–16 GB RAM وقرص SSD مناسب للمرفقات، ثم قياس الاستخدام الفعلي. هذه ليست نتيجة اختبار تحميل ولا ضمانًا لعدد موظفين. بعض الصور، مثل RustFS، تحمل وسم beta في الإعداد الأصلي؛ نختبرها ونسخها الاحتياطي قبل الإنتاج.

نحتاج اسم نطاق فرعي تملكه مثل `support.your-domain.com`، وسجل DNS يصل للسيرفر، وإمكانية استقبال 80 و443، وبريد SMTP فعلي لتأكيد الحساب والدعوات. يجب أن يستطيع السيرفر الوصول أيضًا إلى اسمه العام، لأن روابط S3 الموقعة تستخدم نفس النطاق.

لا يمكن تشغيل PostgreSQL وRedis وعمال ChatbotX داخل استضافة لوحة VINCHI الحالية المبنية على Workers. نحتاج سيرفرًا منفصلًا للمنصة، ثم نصلها باللوحة. لا تشترِ سيرفرًا قبل الاتفاق على حجم الرسائل والمرفقات والتكلفة.

## 6. توليد الإعدادات والتحقق — على السيرفر التجريبي فقط

من مجلد هذه الحزمة، بعد تثبيت Docker من مصدره الرسمي:

```bash
python3 init-config.py --domain support.your-domain.com
```

استبدل النطاق باسمك الحقيقي. افتح `.env` بمحرر محلي آمن، وأكمل `SMTP_FROM` و`SMTP_SERVER`. مثال تنسيق URI فقط: `smtps://USER:PASSWORD@mail.your-domain.com:465`، مع ترميز الأحرف الخاصة في بيانات الدخول حسب URI. اختبر إعداد مزودك؛ لا تلصق البيانات في المحادثة. إذا استعملت اقتباسات مفردة داخل القيمة فاتبع صيغة dotenv الصحيحة.

احتفظ بنسخة مشفرة وآمنة من `ENCRYPTION_KEY` و`BETTER_AUTH_SECRET` وباقي الأسرار. تغيير مفتاح التشفير دون خطة قد يجعل رموز القنوات المحفوظة غير قابلة للقراءة.

```bash
docker compose config --quiet
docker compose pull
docker compose run --rm --no-deps proxy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
```

توقف إذا فشل سحب أي صورة أو التحقق. لا تبدّل إلى `latest` لحل المشكلة دون مراجعة. نجح تحقق Caddy 2.10.2 واختبار توجيهه محليًا بخادم وهمي، بما يشمل رفض السر الخاطئ ومعرّف البوت المكرر ومسارات بديلة. لم نختبر سحب الصور أو تشغيل Compose لعدم توفر Docker. بعد سحب الصور بنجاح سجل digests الفعلية وثبتها قبل الإنتاج.

## 7. إنشاء قاعدة جديدة وتشغيل المنصة

هذه الخطوات تخص **قاعدة staging جديدة**. إذا كان السيرفر يحتوي بيانات قائمة، توقف وخذ نسخة احتياطية متحققة أولًا؛ لا تشغل migration فوق قاعدة مجهولة.

```bash
docker compose up -d postgres redis filesystem
docker compose run --rm filesystem-init
docker compose --profile maintenance run --rm migrate
docker compose up -d builder javascript-executor worker realtime proxy
docker compose ps
```

افتح نطاقك عبر HTTPS، وأنشئ حساب المالك الحقيقي وأكّد البريد. لا تستخدم الحساب التجريبي الموجود في أمثلة المشروع. اختبر تسجيل الدخول والخروج وإعادة تعيين كلمة المرور، وأرسل دعوة لموظف تجريبي وتحقق من الصلاحيات. سجّل workspace ID لكل متجر. قبل الإنتاج راجع من يستطيع التسجيل أو إنشاء workspace على هذا التثبيت، واضبط سياسة التسجيل والوصول المناسبة لشركتك.

افحص صحة الخدمات داخليًا، ورفع صورة وملف خاص وتنزيلهما، واستجابة WebSocket. تحقق أن الملف الخاص لا يصبح متاحًا دون توقيع؛ وجود شاشة تسجيل الدخول وحده لا يكفي لاعتبار التشغيل ناجحًا.

إذا فشل الإقلاع، راجع السجلات محليًا ولا تنسخها كاملة إلى GitHub؛ قد تحتوي على بيانات العملاء أو القنوات. احتفظ بالتشخيص بعد تنقيح الأسرار.

## 8. ربط لوحة VINCHI للقراءة فقط

1. داخل ChatbotX أنشئ API token لمساحة العمل المطلوبة: صلاحية `read_only` ونطاق `contacts` فقط.
2. أضف متجرًا محفوظًا في مساحة VINCHI الخاصة، وسجّل معرفه الداخلي وowner ID الموثوق من بيئة التطبيق.
3. اضبط سر الخادم `CHATBOTX_CONNECTIONS_JSON` بالشكل التالي، مع استبدال كل القيم الرمزية. **لا تحفظه في ملف عام ولا داخل واجهة المتصفح.**

```json
[
  {
    "ownerId": "EXACT_VINCHI_OWNER_ID",
    "storeId": "00000000-0000-4000-8000-000000000001",
    "workspaceId": "EXACT_CHATBOTX_WORKSPACE_ID",
    "baseUrl": "https://support.your-domain.com",
    "apiKey": "READ_ONLY_CONTACTS_TOKEN"
  }
]
```

`baseUrl` هو أصل النطاق فقط دون `/api`. ربط أكثر من متجر يتم بإضافة إعداد مستقل لكل متجر. API tokens في ChatbotX تعمل على مستوى مساحة العمل؛ لا نفترض أنها ترث قيود موظف معين على جهات الاتصال. لهذا يظل المفتاح في الخادم، والفحص محصور بصاحب مساحة VINCHI.

4. افتح لوحة فينشي → **Open my workspace** → **Connections** → اختر المتجر → **Check connection**.
5. «API reachable» مع قائمة فارغة لا يؤكد تطابق workspace؛ أضف جهة اتصال اختبارية غير حقيقية وأعد الفحص. نجاح الفحص يثبت القراءة والمطابقة فقط؛ لا يثبت وصول رسائل أو مزامنة Shopify.

اللوحة الحالية تعتمد على هوية الاستضافة الخاصة بها؛ نقل كودها إلى استضافة أخرى يحتاج مصادقة مستقلة. لا تثق برؤوس الهوية التي يرسلها المتصفح على سيرفر مستقل.

## 9. أول قناة: Telegram تجريبي

الإعداد المرفق يسمح ببوت واحد فقط في أول إطلاق. لا تنقل بوت الإنتاج الآن: `setWebhook` يستبدل وجهته الحالية.

1. أنشئ بوت تجربة عند BotFather واحتفظ برمزه في مكان آمن.
2. وصّله داخل مساحة ChatbotX الصحيحة.
3. ضع المعرف الرقمي للبوت في `TELEGRAM_BOT_ID` داخل `.env`؛ هو الجزء الرقمي قبل النقطتين في token، وتتحقق الأداة منه عبر `getMe`.
4. طبّق إعداد الحماية:

```bash
docker compose up -d --force-recreate proxy
python3 register-telegram.py
```

الأداة تطلب الرمز دون إظهاره، وتستخدم سرًا مولدًا محليًا. لا تسقط الرسائل المعلقة عمدًا. إعادة ربط البوت داخل ChatbotX قد تعيد تسجيل webhook دون السر؛ أعد تشغيل الأداة بعدها. إضافة بوت آخر تحتاج خريطة أسرار مستقلة لكل بوت وتعديل الاختبارات؛ لا تشارك سرًا عامًا بين متاجر مختلفة.

5. تحقق أن طلبًا بلا السر يُرفض:

```bash
curl -i -X POST 'https://support.your-domain.com/integrations/telegram/webhook?botId=YOUR_BOT_ID' -H 'Content-Type: application/json' --data '{}'
```

النتيجة المتوقعة `403`. ثم أرسل رسالة وصورة حقيقية من حساب اختبار بدأ المحادثة مع البوت، ورد من الموظف، واختبر إعادة تشغيل الخدمات. اختبر أيضًا botId غير مطابق أو مكرر، ومسارات بحروف كبيرة وصغيرة؛ لا ينبغي أن تتجاوز الحماية. هذه الحماية تعتمد على مرور كل الحركة عبر Caddy؛ لا تكشف منفذ builder مباشرة.

## 10. Meta وWhatsApp وMessenger وInstagram وTikTok

ابدأ برقم وقنوات اختبار، واضبط تطبيقات مزودي الخدمة وحسابات الأعمال وصلاحياتها. في WhatsApp اليدوي يجب ضبط App Secret لتفعيل فحص التوقيع؛ المسار الذي راجعته يسمح بوضع legacy غير متحقق إذا غاب السر. اختبار رفض webhook المزور شرط تفعيل.

اختبر لكل قناة: رسالة واردة، رد، مرفق، تسليم/قراءة حيث يدعمه API، انقطاع ورمز وصول منتهي، وتجديد الرمز وعدم تكرار الرسائل. Facebook هنا يعني عادة صندوق رسائل الصفحة عبر Messenger؛ إدارة كل أنواع منشورات Facebook وإعلاناته ليست نتيجة تلقائية لهذا الربط. TikTok يخضع لأهلية حسابك ومنطقتك والصلاحيات المتاحة فعلًا.

لا تفترض أن نقل رقم WhatsApp المستخدم حاليًا مع Zoko/respond.io خطوة بلا أثر. نحدد مالك الرقم والـ WABA والمسار المتاح لنقله أو تعايشه، ثم نافذة التحويل والرجوع. لكل قناة مرسل آلي واحد مسؤول عن الرد وقت الانتقال، لمنع التكرار.

## 11. Shopify — الجزء الذي ما زال يحتاج تطويرًا

لم أجد موصل Shopify جاهزًا في مسارات التطبيق والتكاملات التي راجعتها. لذلك لا يكفي نسخ ChatbotX ليحل محل كل وظائف Zoko. نطوّر إضافة التجارة بمراحل:

1. متجر واحد وصلاحيات قراءة محدودة، ثم مزامنة العملاء والطلبات وسجل أحداث موثق.
2. التحقق من توقيع webhook باستخدام الجسم الخام، وربط كل حدث بالمتجر المصرح له، ومنع تكرار المعالجة بالمعرف الفريد.
3. عرض الطلبات وحالة التأكيد والشحن والتسليم بجانب العميل؛ يبقى Shopify مرجع حقيقة الطلبات والمدفوعات.
4. دعم أكثر من متجر دون دمج عملاء متاجر مختلفة تلقائيًا برقم هاتف فقط.
5. استعادة عمليات checkout المتروكة عندما يكون العميل معروفًا وبياناته متاحة للتطبيق؛ لا يمكن التواصل مع كل زائر أو سلة مجهولة.
6. حملات لاحقة للعملاء الموافقين فقط، بقوالب القناة المناسبة وإيقاف الإرسال بعد سحب الموافقة أو إتمام الشراء أو الإلغاء حسب منطق الحملة.
7. أي إجراء يغيّر طلب Shopify يحتاج صلاحية مستقلة واختبارًا وتدقيقًا، بدل تفعيله تلقائيًا مع القراءة.

نثبت نسخة Shopify API ونراجع الوثائق والصلاحيات المتاحة لحساباتك عند التنفيذ. لا تتضمن الحزمة الحالية مزامنة أو checkout recovery نشطة.

## 12. تطبيق الموبايل

نستخدم Fork الموبايل الموجود، ولا ننشره قبل نجاح API والويب. اقرأ تعليمات المستودع ووثائق Expo المطابقة للإصدار 57 قبل تعديله.

ملفا `mobile/brand.json` و`mobile/environment.example` قالبان فقط. انسخ brand إلى `brands/vinchi/brand.json` وأضف الصور المطلوبة. استبدل `com.example.vinchi.support` بمعرّفات تملكها، واربط **حساب Expo/EAS الخاص بك** ثم حسابي Apple/Google وFCM. لا تستخدم مشروع EAS أو أسرار النشر الخاصة بالمطور الأصلي.

`API_BASE_URL` هو `https://support.your-domain.com` دون `/api` لأن العميل يضيفها. `WS_URL` هو `https://support.your-domain.com/ws`. أضف مخطط التطبيق المخصص إلى trusted origins المسموح بها في backend بعد مراجعة آلية المصادقة.

وجدت أن إعداد أيقونة iOS يشير إلى `assets/expo.icon` مباشرة؛ يحتاج تعديلًا واختبارًا حتى لا ينشر تطبيق فينشي بأيقونة المشروع الأصلي. مجلدات brands المخصصة مستثناة افتراضيًا من Git؛ نحفظ علامة فينشي في مستودعها الخاص أو نستثني مسارها بعناية. لم تُصنع صور الهوية أو نسخة APK/IPA بعد.

## 13. اختبارات قبول الإطلاق

لا نلغي Zoko/respond.io قبل نجاح هذه الحالات بحسابات اختبار ثم مجموعة صغيرة من المحادثات:

- حساب مالك وموظفين اثنين، فصل الصلاحيات والمتاجر، وتعطيل موظف وفقدانه الوصول.
- وارد وصادر ومرفقات وRealtime، واستعادة العمل بعد restart، وعدم ازدواج الإرسال.
- رفض webhook غير صحيح في كل قناة؛ منع تجاوز الحماية بمنفذ مباشر.
- ملف خاص لا يمكن قراءته دون صلاحية؛ ملفات عامة للقراءة فقط.
- ترحيل بيانات محدود مع مراجعة أعداد العملاء والمحادثات والربط وعدم دمج خاطئ.
- Shopify: طلب جديد وتحديث شحن وإلغاء، وتكرار webhook ووصوله بترتيب مختلف، وتحقق حالات checkout والموافقة.
- اختبار عربي وRTL على أجهزة فعلية، والتنبيهات والعودة من الخلفية في الموبايل.
- قياس تأخر الرسائل وطول الطوابير واستهلاك الذاكرة والقرص عند الحمل المتوقع، وليس مجرد عدد حسابات موظفين.
- استرجاع نسخة احتياطية على سيرفر معزول بنجاح، ومراقبة فشل العمال والبريد والتخزين.

## 14. النسخ الاحتياطي والترقية والرجوع

خذ نسخة متسقة من PostgreSQL وملفات S3 معًا، وأسرار التشفير في مخزن منفصل وآمن، وإعدادات الإصدار. عين جدول احتفاظ ومسؤولًا للنسخ والاستعادة، واختبر الاستعادة قبل إدخال بيانات حقيقية. لا يكفي حفظ كود GitHub.

مثال نسخ قاعدة staging إلى ملف بصلاحيات مقيدة، من المجلد الصحيح:

```bash
umask 077
mkdir -p backups
docker compose exec -T postgres pg_dump -U chatbotx -d chatbotx -Fc > backups/chatbotx.dump
```

هذا مثال لقاعدة البيانات فقط؛ أكمله بنسخ التخزين والأسرار. لا تستبدل نسخة سليمة سابقة بملف فارغ بعد فشل الأمر. احفظ النسخ خارج السيرفر، ولا تضف `backups/` إلى Git.

للترقية: نسخة staging من البيانات، نسخة احتياطية متحققة، مراجعة migration، تثبيت إصدار ودجست جديدين، تشغيل migration مرة واحدة ثم الخدمات، واختبارات القبول. الرجوع بعد تغيير مخطط البيانات قد يحتاج استعادة قاعدة وتخزين متوافقين؛ إعادة صورة قديمة وحدها ليست خطة رجوع كافية. لا تستخدم `docker compose down -v` مع بيانات مهمة.

## 15. المطلوب منك للخطوة التالية

1. تحديد السيرفر والدومين لتجربة staging؛ نسخ GitHub والصلاحية متاحتان بالفعل.
2. هل لديك VPS بالفعل؟ اذكر المزود والمعمارية والذاكرة دون كلمة مرور أو مفتاح خاص.
3. النطاق الفرعي المراد استخدامه، وأسماء متاجر `myshopify.com`، وعدد الموظفين المتزامنين والحجم التقريبي للمحادثات اليومية.

بعدها نبدأ بتشغيل staging ومراجعة السجلات والاختبارات، ثم قناة اختبار، ثم Shopify. أستطيع إعداد الفروع والكود والاختبارات باستخدام الصلاحيات المتاحة؛ إنشاء حسابات المزودين وتأكيد ملكيتها وتوفير أسرارها يتم في واجهاتها الآمنة.
